# APEX Below-Zero-Trust Policy — Zero-Consequence Edition

Status: **design target with feasibility boundaries; not an implementation or guarantee of zero overhead**.
This document preserves the intended direction: assume compromise, keep trust short-lived, perform verification in parallel where safe, minimize hot-path cost, and make recovery fast. It does not override the protocol's consistency, durability, or evidence gates.

## Core principle

Assume every component may be compromised. Hardware attestation is bounded and time-limited evidence; runtime and isolation boundaries are not inherently trustworthy; peers can collude; measurements are historical; identities and keys have bounded authority; and proofs must be freshly bound to the operation and current policy epoch.

The performance goal is to make verification overhead as small and predictable as possible through batching, hardware acceleration, precomputation, caching of non-authoritative work, and parallel execution. **Zero observable cost and absolute security cannot be guaranteed across arbitrary hardware, workloads, partitions, and adversaries.** Measure overhead and define service objectives rather than asserting it is zero.

## 1. Speculative execution and rollback

- Speculation may run only before irreversible effects, or against an isolated staging area with a commit gate.
- External messages, user-visible success, key release, destructive writes, and authoritative CAS mutations must not escape before the required authorization/consensus/durability condition is met.
- Rollback can revert controlled internal state only while all effects remain inside a transactional boundary. It cannot mathematically erase data already observed by an attacker, retract a message already consumed externally, or undo physical side effects.
- Use short-lived, forward-secure operation tickets bound to operation digest, namespace, expected generation, identity, nonce, and policy epoch. Tickets grant limited authority, not proof that the node is uncompromised.
- On failed verification, fence the affected identity/epoch immediately in local enforcement, reject new work, quarantine the node, and distribute signed revocation evidence. Remote revocation is bounded by network reachability and cannot be instantaneous during a partition.

**Invariant:** no operation may be reported as committed until its defined commit conditions are met. If speculative work fails validation, staged state is discarded and no authoritative side effect has occurred.

## 2. Continuous micro-verification

- Lightweight integrity telemetry may supplement periodic hardware quotes: secure boot/runtime measurement events, monotonic counters, watchdogs, memory-safety signals, challenge-response, anomaly indicators, and hardware-supported control-flow or isolation evidence where the platform actually supports them.
- Telemetry is a detection signal, not a universal proof of runtime integrity. Performance counters and encrypted traces can be noisy, incomplete, unavailable, or controlled by compromised software.
- Define telemetry provenance, anti-replay, freshness, coverage, tamper response, false-positive handling, and independent verification. Do not accept a signal as trustworthy merely because it was generated by a local runtime.
- Run heavyweight attestation at boot/rejoin and after firmware, boot-chain, hypervisor, runtime, isolation-policy, security configuration, or key changes. High-risk operations may require fresh challenge-bound evidence.
- Measure CPU, latency, bandwidth, energy, false-positive, and detection-latency costs on each supported hardware class.

## 3. Precomputation and cached proofs

- Precompute cryptographic material that is safe to precompute (for example, signature preparation, session setup, Merkle paths, or proof scaffolding).
- Cached evidence is only an optimization. Before use, bind it to a fresh challenge/operation, current identity and policy epochs, expiry, recipient, and nonce. A cache hit must never bypass freshness, revocation, or authorization checks.
- Do not call cached proofs “perfectly forward-secure” unless the protocol and key-erasure model actually establish forward secrecy. Epoch advancement alone does not.
- Keep one-time tokens replay-resistant with durable or session-scoped replay tracking. Define behavior when peers have stale epoch state.

## 4. Hierarchical leases and revocation

- Use short inner operation tickets under a bounded outer membership lease. Each lease specifies scope, namespace, operations, identity, policy/membership epoch, expiry, and renewal requirements.
- Local enforcement can stop use of a lease immediately when local trusted enforcement detects failure. It cannot guarantee remote peers receive revocation instantly, particularly during partitions.
- Remote peers reject expired leases, stale epochs, and revocation-list versions older than policy allows. High-risk mutations require a current quorum certificate and fencing token.
- Revocation dissemination must be authenticated, replay-protected, independently propagated, and auditable. Speculation does not make a remote network broadcast reversible.
- Define a maximum exposure window and safe degraded behavior. If the revocation/epoch freshness bound cannot be met, privileged operations fail closed while explicitly classified read-only/non-critical paths may continue.

## 5. Transparent end-to-end data protection

- Classify data and capabilities at the API boundary; default sensitive or unknown-classification data to the stronger protection path.
- Protect high-value data with envelope encryption and, where justified, threshold key management. Keys are released only to authorized, currently eligible contexts.
- A runtime that handles plaintext is in the trusted computing base for that plaintext. If the runtime must remain untrusted, use an architecture that demonstrably keeps plaintext outside it (for example, supported confidential execution or client-side encryption); do not claim this property merely because a wrapper exists.
- Threshold schemes require an explicit threshold, independent holders/failure domains, key refresh/revocation, and recovery tests. Thresholds do not help if the required share holders collude or share a correlated compromise domain.
- Keep application APIs simple, but surface conflicts, degraded durability, unavailable quorum, and recovery status instead of hiding material safety failures.

## 6. Adaptive, non-gameable verification

- Increase verification based on signed, auditable policy and multiple signals; never allow a local risk score, VRF output, or entropy source alone to relax required baseline checks.
- Use verifiable randomness only for the property it provides (for example, unpredictable sampling). It does not prove a node honest, make an input non-gameable, or replace authorization and consensus.
- Keep minimum security gates invariant under load. When capacity is insufficient, reduce optional work, defer low-priority tasks, or expose degraded availability; do not silently weaken attestation, quorum, encryption, or namespace isolation.
- Define and test anti-thrashing, false-positive appeal/recovery, and resource-exhaustion behavior.

## 7. Hardware offload and data-path design

- Offload supported cryptography and telemetry to hardware where benchmarks show a benefit. Verify the exact hardware/firmware feature and its threat model; do not assume a TPM/TEE can continuously prove arbitrary application behavior.
- Pipeline transfer and verification only where the consumer cannot observe or commit unverified data. Validate content hashes, authorization, epoch, and commit certificate before exposing a value as authoritative.
- Benchmark tail latency, throughput, CPU, memory, energy, and behavior during degraded conditions. “Native speed” is a measured target, not a protocol guarantee.

## 8. Required security invariants

1. **Freshness:** no expired, replayed, revoked, or stale-epoch evidence authorizes new privileged work.
2. **No speculative external commit:** irreversible or externally visible effects wait for the required authorization and consistency condition.
3. **Partition safety:** a partition cannot produce two accepted commits where the declared model promises linearizability. If quorum is absent, authoritative writes fail or return an explicit degraded/conflict result.
4. **Durability honesty:** “durable” is reported only after verified acknowledgements from the required number of independently evidenced failure domains. Commit and target replication may be distinct states.
5. **Limited compromise blast radius:** one node/key cannot unilaterally change policy, membership, revoke all peers, or satisfy a multi-domain quorum.
6. **Change invalidation:** firmware, boot chain, hypervisor, runtime, storage adapter, isolation policy, security configuration, and relevant key changes invalidate prior trust until fresh accepted evidence is obtained.
7. **Recovery:** node loss, key compromise, and replica corruption have tested recovery paths; no irreplaceable data or sole recovery key depends on one piece of silicon.
8. **Evidence:** specified, implemented, automated-tested, live-tested, and independently verified are separate states. No claim advances without linked evidence on the exact commit/runtime.

## 9. Acceptance and performance gates

- Threat tests: post-attestation compromise simulation, replay, stale epoch, delayed revocation, malicious peer, colluding sub-threshold peers, partitioned CAS, discovery eclipse, leaked capability, replica loss/corruption, key rotation, and firmware-policy transition.
- Durability tests: independent operator-controlled hosts, process and host restart, peer loss, recovery, repair, quorum receipts, and independent read-back.
- Performance tests: benchmark baseline versus controls under normal, high-load, partition, and attack conditions; report p50/p95/p99 latency, throughput, CPU, memory, bandwidth, energy where measurable, and failure/degraded behavior.
- Set explicit service-level objectives for overhead and detection/revocation/recovery time. Any target such as “milliseconds” must be demonstrated on specified hardware/network conditions and include partition behavior.
- Roll out first to a non-critical namespace; preserve old data until recovery is independently proven. Do not merge or deploy while required security gates are open.

## Guarantee boundary

This policy aims for maximal distrust with minimal practical overhead. It does **not** promise zero observable cost, instantaneous global revocation, perfect rollback of external effects, continuous hardware proof, immunity to colluding threshold peers, or absolute security. Those are physical/distributed-systems limits, not gaps that wording can remove.
